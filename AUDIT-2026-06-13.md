# Tempo PWA — Principal-Engineer Deep Audit

**Date:** 2026-06-13 · **Branch:** `main` @ `593db7c` · **Reviewer:** Claude (principal-engineer audit)
**Scope:** Risk-weighted full sweep. Deep on the cloud-sync stack (engine + 7 merge modules + schema/persistence/buffer + rules + Admin-SDK council), meds dose-logging, import/export, the platform seam, and all UI render paths. Skimmed: `css/`, `docs/`, `node_modules/`, the iOS shell (`ios/`), generated `www/`, and `package-lock.json`. **Read-only audit — no source was modified.**

---

## Verdict

**This is mature, unusually disciplined code for a no-framework app.** The timing engines are clean (drift-free wall-clock math holds up), the data-dictionary/ADR discipline is real, the firestore rules are correct *and* carry an excellent comment about cumulative rule evaluation, secrets are properly gitignored with a clean history, and there are 1,243 engine tests. **No Critical findings** — nothing destroys user data outright or bypasses authz.

The risk is **concentrated almost entirely in one place: the steady-state cloud-sync layer.** The flagship "LIVE by default" sync has a structural gap — it converges the *cloud* but, for 5 of 7 stores, never writes remote changes back to *local* storage — so cross-device sync silently doesn't work for meds, history, BFRB, mood, and distractions after a device's first hydrate. That's the headline. The rest is a long tail of correctness/reliability/XSS-hardening items, most of them small.

### How these findings were produced (and how trustworthy they are)

17 subsystem finder-agents read their assigned files in full and produced 88 raw findings. **Every one was then handed to an independent adversarial verifier** that re-opened the cited code and tried to *refute* it (default verdict = not-real). 20 were rejected outright (vague, already-guarded, or contradicted by the code) and 11 were severity-downgraded. **68 survived.** I then personally re-verified all 4 High themes against the literal source before writing them up. Treat High/Med as high-confidence; the Low tier is verifier-confirmed but presented condensed.

## HIGH

### H1 · `importAllData` wipes history before a non-atomic restore — a mid-loop failure destroys data
- **Severity:** High · **Category:** Data integrity · **Effort:** S
- **Where:** `js/export.js:250-256`
- **What's wrong:** `importAllData` does `await History.clearAll()` (line 251) and *then* loops `await History.addSession(s)` over the backup with no `try/catch`, no transaction, and no per-element validation. The session array elements aren't checked to be objects first (`History.addSession` immediately dereferences `session.id` / spreads `...session`).
- **Why it matters:** Import is the one place untrusted JSON (a file the user picked, possibly hand-edited or produced by another tool) becomes persisted state. If `addSession` throws partway — a single malformed element (`"x"`, `null`, `42`), a quota error, or an IDB transaction abort — history has already been cleared and is left **partially restored with no rollback**. The user loses real history to a botched restore of a backup that was supposed to protect it.
- **Fix:**
  ```js
  // Validate + stage first, clear only once parse/shape is known-good.
  if (Array.isArray(data.sessions)) {
    const valid = data.sessions.filter(s => s && typeof s === 'object' && !Array.isArray(s));
    await History.clearAll();
    for (const s of valid) {
      try { await History.addSession(s); sessionsImported++; }
      catch (e) { console.warn('[import] skipped bad session', e); } // don't abort the rest
    }
  }
  ```
  Ideally do the clear+bulk-put in a *single* IDB transaction (History already has a privileged bulk-write path used by hydrate) so the restore is atomic.

### H2 · `getBFRBTrend` double-counts every Flow/Pomodoro catch
- **Severity:** High · **Category:** Correctness · **Effort:** S
- **Where:** `js/analytics.js:332-408` (the two `stamps.push(...)` sources, lines 339-346 and 353-366)
- **What's wrong:** The trend builder collects BFRB timestamps from **two sources into one array with no cross-source dedup**: (1) the legacy in-session tally `session.bfrbs[]` on flow/pomodoro history records, and (2) the consolidated `BfrbEvents.getAll()` stream — which is the F3 "single source of truth" that *owns the migration of those same in-session catches*. Any catch that exists both as a migrated event and as a surviving `session.bfrbs` entry is counted twice. The inline comment claims output is "byte-equivalent post-migration," but nothing dedupes the two streams.
- **Why it matters:** This is a behaviour-change app whose entire BFRB loop depends on the user trusting the frequency trend. A silently 2×-inflated count (and the derived `ratePerHour`, `bySource`, hourly histogram) misrepresents progress — the user acts on wrong data.
- **Fix:** Dedupe by a `(timestamp, source)` signature before bucketing, or — cleaner — drop the `session.bfrbs` branch entirely now that `BfrbEvents` is the source of truth (confirm the migration leaves no un-migrated `session.bfrbs`, then delete lines 339-346).
  ```js
  const seen = new Set();
  const add = (timestamp, source) => {
    const k = timestamp + '|' + source;
    if (seen.has(k)) return;
    seen.add(k); stamps.push({ timestamp, source });
  };
  ```
  Add the regression test that's currently missing (see Low/Tests).

### H3 · F13 write-gate **silently drops** user writes when stuck in `'error'` (no deferral)
- **Severity:** High · **Category:** Data integrity · **Effort:** M
- **Where:** `js/persistence.js:34-36` (`canWrite()`); drop sites: `js/history.js:215/277/298/314/337/368`, `js/meds.js:556`, `js/bfrb-events.js:333`, `js/mood.js:184`, `js/distractions.js:383`, `js/presets.js:41/57/73`, `js/recovery-ui.js:45`. `'error'` is set across the hydrate/upload paths (`js/sync-engine.js:779,820,1104,1137,1166,1481,1518,…`).
- **What's wrong:** Every gated writer does a bare `if (!canWrite()) return;` — a **silent drop**, not a deferral. `canWrite()` is true only in state `'ready'`. The hydrate / initial-upload paths flip the gate to `'error'` on failure and **deliberately do not auto-clear it** (sync-engine.js:664-666: *"Don't auto-clear"*), and the state is persisted in `localStorage` (`tempo_sync_state`) — so it survives reloads. The offline buffer (`SyncBuffer.enqueue`) *bypasses* the gate, but the gated write sites never route to it.
- **Why it matters:** After a failed hydrate or first-sign-in upload, the gate sits at `'error'` indefinitely, and **every subsequent dose log, BFRB catch, mood entry, history session, distraction, and preset write is silently discarded** — across reloads — until the user happens to notice and manually reconciles. Silent loss of *medication-logging* data is the worst-case here. (Note: the steady-state merge cycle self-heals to `'ready'` in its `finally`, so this is specifically the hydrate/upload-failure window, not every transient sync error — which is why it's High, not Critical.)
- **Fix:** When the gate is closed, **defer instead of drop** — route the write through `SyncBuffer.enqueue` (which already bypasses the gate by design) so it drains when sync recovers; and surface a visible "writes paused — sync error, tap to reconcile" banner instead of failing silently. At minimum, the `'error'` state must have a user-visible recovery affordance wired to the gate, not just the console.

### H4 · ★ Steady-state "live" sync never applies remote arrivals to **local** for 5 of 7 stores *(highest impact)*
- **Severity:** High · **Category:** Correctness / Data integrity · **Effort:** L
- **Where:** `js/sync-merge-meds.js:248-303`, `js/sync-merge-history.js:204-373`, `js/sync-merge-bfrb.js:50-270`, `js/sync-merge-mood.js`, `js/sync-merge-distractions.js:145-…`. Contrast with the two correct ones: `js/sync-merge-rest-log.js:290` and `js/sync-merge-presets.js:260` (both call a `_reconcileWriteRaw` local-apply). Engine path: `js/sync-engine.js` — onSnapshot → `_scheduleStoreMerge` → merge fn; store adapters use `write: writeStub` (line 138/144-150); `hydrateFromCloud` short-circuits on `tempo_sync_hydrated_all === '1'` (line ~1050).
- **What's wrong:** In steady state, an `onSnapshot` (or 300s poll) fires the per-store merge. Each merge reads local, unions with cloud, and writes the merged set **back to Firestore via CAS** — but only `rest_log` and `presets` then write the merged result back into **local** storage. The other five do not:
  - `bfrb_events` / `mood_events`: read `getAll()`, write cloud only — no local store write at all.
  - `history`: reads `History.getSessions()`, writes cloud only — never `addSession`/bulk-put locally.
  - `meds`: subtler — it does `localMeds = MedsManager.all().map(m => m.getState())` (a **snapshot copy**), mutates `copy.doseLog = result.entries`, then calls `onMergeComplete(med.id)` which runs `recomputeLastTakenAt()` + `saveAll()` on the **live** med — whose `doseLog` was never given the cloud doses. The reconciled doses reach the cloud, not the live local med.

  Because `hydrateFromCloud` (the only local-writer) short-circuits on the persisted `tempo_sync_hydrated_all` marker, **a reload does not fix it either** — remote changes to these 5 stores are invisible on a device for the rest of its life until the markers are cleared (sign-out / manual reconcile). Worse, the test suite *asserts* this no-writeback behavior (see Low/Tests), locking the defect in.
- **Why it matters:** This is the flagship Phase-9 feature. As shipped, cross-device sync genuinely works for only 2 of 7 stores. Log a dose on your phone; your laptop never shows it (and vice-versa) until a re-hydrate. No data is *lost* (the cloud retains everything; re-hydrate recovers it), but the feature does not deliver its core promise for meds/history/BFRB/mood/distractions, silently.
- **Fix:** Give the 5 merges the same local-apply the working two have. Each store's data module needs a privileged `_reconcileWriteRaw(merged)` (bypassing the F13 gate, exactly as `RecoveryUI`/`Presets` do), and each merge fn must call it after building `mergedRecords`:
  ```js
  // sync-merge-bfrb.js, after mergedRecords is built and before/after CAS writeback:
  if (typeof BfrbEvents._reconcileWriteRaw === 'function') {
    BfrbEvents._reconcileWriteRaw(mergedRecords);   // apply cloud-origin events locally
  }
  ```
  For meds, apply `result.entries` to the **live** med (`MedsManager.applyMergedDoseLog(med.id, result.entries)`) rather than to the throwaway snapshot, then `onMergeComplete`. Then **replace the tests that assert no-writeback** with ones that assert a cloud-origin record is locally queryable after `merge()`.

## MEDIUM

### M1 · Steady-state listeners + interval are never torn down on sign-out / flag-disable
- **Reliability · S · `js/sync-engine.js:2575` (`stopSteadyState` defn), `269-272` (`disable`), `208-237` (`_maybeAutoHydrate`); UI: `js/tempo-nav.js:667,700-709`.** `stopSteadyState()` has **zero production callers** (only tests). `disable()` only calls `SyncFlag.disable()` (its "B-2 will tear down listeners" comment was never implemented); the auth-change handler `_maybeAutoHydrate` just `return`s on `user === null`. So after sign-out or disabling sync, the 5-min interval keeps firing and the 7 `onSnapshot` listeners + `visibilitychange`/network handlers stay registered until page reload. *(Bounded: the orphaned interval's cycle early-returns on null user, and listeners drop while the tab is backgrounded — so it's a leak, not a write storm. Downgraded High→Med by verification.)* **Fix:** call `stopSteadyState()` in `disable()` and in the `!user` branch of the auth-change handler.

### M2 · Self-triggering merge loop: unconditional CAS writeback + no self-write filter
- **Reliability · M · `js/sync-firestore.js:454-464` (`_onNext`), `js/sync-engine.js:2398-2408`, `js/sync-merge-*.js` writeback loops; `js/schema.js:53-58`.** The `onSnapshot` wrapper fires the engine callback on *every* snapshot — it never checks `snapshot.metadata.hasPendingWrites` or uses `docChanges()`. Merges re-write **every** record each cycle (no dirty check; `Schema.stamp` doesn't bump `updatedAt`, so even a no-op cycle re-writes identical content). With ≥2 devices online, each store enters a perpetual post-debounce (~1 Hz) merge/CAS-write loop on no real change — burning Firestore reads/writes/battery and flipping `SyncState` to `'hydrating'` every second. **Fix:** ignore snapshots where `metadata.hasPendingWrites` is true; and/or skip the CAS write when the merged record equals the cloud doc.

### M3 · `onSnapshot` error branch leaves a dead listener in `_listenerUnsubs`
- **Reliability · S · `js/sync-engine.js:2398-2406`.** On an error envelope (`snap.ok === false`, e.g. transient permission-denied) the handler emits `listener-disconnected` and returns **without** calling the store's unsub or deleting its registry entry. Because `_subscribeAllStores` skips any key already in `_listenerUnsubs`, that store is left permanently without a real-time listener for the session — cross-device propagation silently degrades after one recoverable blip. **Fix:** in the error branch, call the stored unsub, `_listenerUnsubs.delete(key)`, clear the debouncer, *then* emit — so the next pass can re-arm it.

### M4 · Log-past-session: equal start/end silently records a 24-hour session
- **Correctness · S · `js/history-ui.js:491-499`.** `if (endDate <= startDate) endDate.setDate(endDate.getDate()+1)` (meant for cross-midnight) *also* fires when start === end, producing `durationMs = 86_400_000`; the later `if (durationMs <= 0)` guard is then dead code (rollover already forced `end > start`). A user entering identical times gets a silent 24-hour session written to IDB and synced, corrupting focus-minute/daily rollups. **Fix:** compute `durationMs` from raw inputs and reject `=== 0` *before* the cross-midnight rollover.

### M5 · History merge re-writes every session to Firestore each cycle (write amplification)
- **Reliability · M · `js/sync-merge-history.js:311-341`.** The writeback loop does `tx.get + tx.set` for *every* merged session every cycle with no change detection — hundreds of reads+writes per cycle for a user with a large history, ×devices ×every remote burst. **Fix:** only `tx.set` records genuinely created/changed this cycle (local-only ids, LWW-flipped, or phaseLog-union-changed). Same root cause as M2.

### M6 · `council/.env.secrets` is world-readable (0644)
- **Security · S · `council/.env.secrets` (mode `-rw-r--r--`); sourced by `council/run-synthesis.sh:42-45`.** The file holds `TEMPO_UID` (the Firebase uid the Admin SDK writes the whole synthesis subcollection under) and the path to `GOOGLE_APPLICATION_CREDENTIALS`, and is *designed* to also hold a Slack webhook / Twilio token. World-readable on a multi-account machine. *(Properly gitignored — this is a filesystem-perms issue, not a committed-secret one.)* **Fix:** `chmod 600` the file and the SA key it points at; add a preflight in `run-synthesis.sh` that fails if perms aren't `600`.

### M7 · Attribute-context XSS class — `escapeHtml` does not escape quotes *(consolidates 6 sites)*
- **Security · S (one central fix) · root cause `js/dom-utils.js:1-8`.** `escapeHtml` serializes via `element.innerHTML`, which per spec escapes only `& < >` — **not `"` or `'`**. It's safe in *element-text* context but unsafe wherever its output is interpolated into a **quoted HTML attribute**. Confirmed sites:

  | Site | Attribute | User-controlled value | Reach |
  |---|---|---|---|
  | `js/recovery-ui.js:354-371` | innerHTML (no escape *at all* + no type check) | `sleep.hours` / `quality` from `rest_log` | **sync-reachable** (poisoned rest_log from another device) |
  | `js/flow-ui.js:762,765` | `aria-label` | Todoist task text | **external data** (Todoist) |
  | `js/pomodoro-ui.js:1448-1452` | `title=` | Pomodoro goal / Todoist text | **external data** |
  | `js/meds-ui.js:111-112` | `aria-label` | med name | sync-reachable |
  | `js/history-ui.js:151,250` | `data-filter-tag`/`data-tag` | tag (≤20 chars, fits `"onpointerover=…`) | sync-reachable |
  | `js/cooking-ui.js:161` | `value=` | cooking-timer name | self only (Low) |

  **Why it matters:** honest calibration — this is a single-user personal PWA, so most vectors are self-inflicted. But three are *not*: Todoist task text (external), and any value arriving via cloud sync from a poisoned/compromised device (the recovery-ui and tag paths). A successful injection runs in the app origin → can exfiltrate the Firebase session, the device-local Todoist token, and all synced health data. **Fix (one line, closes all attribute sites):**
  ```js
  function escapeHtml(str) {
    return String(str ?? '')
      .replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;')
      .replace(/"/g,'&quot;').replace(/'/g,'&#39;');
  }
  ```
  Separately, `recovery-ui.js:354-371` interpolates raw values with **no** escaping/typing — coerce `sleep.hours`/`quality` to numbers (or escape) there regardless.

### M8 · `importAllData` doesn't validate session elements are objects
- **Correctness · S · `js/export.js:252-254`.** Same code as H1; called out separately because the element-shape guard is the minimal stand-alone hardening even if atomicity (H1) is deferred. Mirror the existing `rec && typeof rec === 'object' && typeof rec.id === 'string'` guard the meds branch already uses (export.js:286).

### M9 · Native (iOS) steady-state push is silently disabled — all CAS writebacks throw *(KNOWN, expand)*
- **Reliability · L · `js/sync-firestore.js:331-343`.** `runTransaction()` throws `kind:'unknown'` ('native parity pending') on `isNative`, and all six steady-state merge writebacks use *only* `runTransaction` (no `setDoc` fallback). On iOS — a shipped target — events logged on the phone never sync up after the first reconcile, with no surfaced error. Tracked as backlog #3, but **make the gap visible**: emit a distinct `native-writeback-unsupported` event instead of a silent `skipped++`, so the UI can warn. (Compounds with H4: on iOS, sync is broken in *both* directions for these stores.)

### M10 · Cooking-timer id collision on rapid add
- **Correctness · S · `js/cooking-ui.js:71`.** `const id = Date.now().toString(36)` with no disambiguator and no add-button debounce → two adds in the same ms get identical ids; handlers resolve via `.find(c => c.id === id)` and control/delete the wrong timer. **Fix:** append `'-' + Math.random().toString(36).slice(2,6)` (matches the localTag pattern elsewhere).

### M11 · Service worker shows background notifications but has no `notificationclick` handler
- **Reliability · S · `sw.js:187-216`.** Every web background alarm calls `showNotification(..., {requireInteraction:true})` but there's no `notificationclick` listener — tapping the notification is a no-op and leaves a sticky notification. Background notifications are the whole point of the backgrounded-timer feature. **Fix:** add a `notificationclick` handler that `clients.matchAll` → focus an existing window or `clients.openWindow('/')`.

### M12 · `InstanceManager` (core stopwatch/timer persistence) has zero tests
- **Tests · M · `js/instance-manager.js:83-156`.** The module that persists the app's primary surface (`multi_state`, multi-instance + primary tracking, tab-close survival) is not loaded in `tests/index.html` and has no test. Highest criticality-vs-coverage gap in the app. **Fix:** add `tests/instance-manager.test.js` covering the MAX_INSTANCES cap, primary-swap, and saveAll→loadAll round-trip.

### M13 · `SyncState` (the F13 gate) real implementation is never loaded or tested
- **Tests · M · `js/persistence.js:7-47`.** `persistence.js` isn't in `tests/index.html`; every sync test installs a hand-rolled `window.SyncState` stub, so the real gate — which *every* synced write consults (and whose H3 bug lives) — is never exercised: fail-open-on-garbage, reject-unknown-on-`set`, `canWrite iff 'ready'`. **Fix:** load it in the harness and add a small suite. (Would have caught H3's drop-vs-defer behavior.)

### M14 · `getMedAdherence` denominator is the full window even for meds created mid-window
- **Correctness · M · `js/analytics.js:461-479`.** Adherence = doses / full-window-days even when the med was added partway through, structurally understating adherence for new meds. **Fix:** clamp the denominator to `max(1, days since med creation)` within the window.

## Top 5 fixes I'd make today

1. **H4 — wire cloud→local writeback into the 5 broken merges.** The flagship feature is silently non-functional for meds/history/BFRB/mood/distractions. ## Three structural improvements for later

1. **Make "apply remote to local" a first-class, uniform step in the merge contract.** H4, M9 (native), and several Low items all stem from the same thing: each of the 7 merges hand-rolls its own data flow, and 5 of them forgot the local-apply leg while 2 remembered. Define one merge interface — `{ readLocal, readCloud, merge, writeCloud (CAS), writeLocal }` — so a store *cannot* be added without a local-apply, and unit-test the contract once for all 7. This would have made H4 structurally impossible.

2. **Split `sync-engine.js` (2,627 lines) and give the gate/listener lifecycle a single owner.** The dead `stopSteadyState()` (M1), the dead-listener-on-error (M3), the self-triggering loop (M2), and the never-cleared `'error'` gate (H3) are all lifecycle/teardown bugs in one giant module where "who tears down what, when" is diffuse. Extract a `SyncLifecycle` (init/enable/disable/sign-out/visibility/network → arm/disarm) that owns the interval, the listener registry, and the `SyncState` transitions, with explicit enter/exit for each state. The merge math is already well-factored; the *orchestration* is where the bugs cluster.

3. **Add a thin layer of UI/integration tests around the render + import paths.** The engine layer is genuinely well-tested (1,243 cases), but every confirmed XSS (M7), the import data-loss window (H1), the `notificationclick` gap (M11), and the InstanceManager/SyncState gaps (M12/M13) live in the *untested* UI/persistence-wiring seam. The Playwright MCP is already wired (`.mcp.json`) — a dozen DOM-level tests (render a tag with a `"` and assert no attribute injection; import a malformed backup and assert history survives; tap a background notification) would cover the exact class of bug the engine suite structurally can't see.
