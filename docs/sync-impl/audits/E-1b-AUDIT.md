## Goal

Land the load-bearing plumbing for Stage E's steady-state merge loop without making any merge decisions or shipping any per-store merge logic. The dispatcher (`_runMergeCycle`) iterates the existing `SYNCED_STORES` registry in `js/sync-engine.js` and invokes each store's `merge(snapshot)` function inside a per-store try/catch so one bad store can't abort the loop. The 4 new `js/sync-merge-*.js` files ship as IIFEs whose `merge()` body is `throw new Error('not implemented until E-1{c,d,e}')` — they exist so the dispatcher is exercise-able + testable in isolation (per the auditor's Pick B lean on TODO #1). The `runTransaction` wrapper replaces B-3's stub at `js/sync-firestore.js:284-285` with a real Firestore CAS implementation: read the remote doc inside the transaction, parse `schemaVersion`, refuse-writeback if `remote.schemaVersion > local SCHEMA_VERSION` (new normalized error `kind: 'refuse-writeback'`), else write the new record. Web-only in E-1b; native plugin parity is a documented follow-up (per Pick A on TODO #5).

## Risks

| Risk | Likelihood | Blast radius | Mitigation |
|------|------------|--------------|------------|
| **CAS atomicity broken — schemaVersion read NOT inside the transaction** | low | **data-loss (HIGH)** | If the `schemaVersion` read happens via a separate `getDoc` outside `runTransaction.get`, a write-after-read race can clobber a future-schema record between the read and the transaction-internal write — defeating the entire F19a CAS gate. **Mitigation:** Pick A on TODO #5 sub-decision 5a explicitly bans field-mask reads outside the transaction. The implementer MUST use `tx.get(ref)` inside the transaction callback (the Firestore SDK's transaction API). Test case: "refuse-writeback path triggers when remote.schemaVersion increments mid-transaction" — mock the SDK's `runTransaction` to simulate a stale read followed by a remote update; assert the transaction re-reads + re-checks and refuses on the second pass (Firestore's retry semantics handle this automatically, but the test confirms our wrapper honors it). |
| **Native plugin gap — iOS device tries to call `runTransaction` on a steady-state tick** | low (was med w/o gate) | **data-correctness (med)** | E-1b is web-only for the CAS wrapper. If the `tempo_sync_steady_state_enabled` flag is somehow set to `'1'` on a native iOS Capacitor build, the dispatcher would invoke merge functions that (when wired in E-1c+) would attempt `SyncFirestore.runTransaction(...)` and hit the explicit "native parity pending" throw. **Mitigation:** (1) Per Pick C on TODO #4, the steady-state flag is default off — no native user hits this path unless they explicitly enable a dev flag they shouldn't know about. (2) The native branch throws a normalized error with `kind: 'unknown'` and message "native parity pending" — the dispatcher's per-store try/catch catches it and `emit('merge-error', ...)` so the failure is visible but doesn't cascade. (3) Document the gap in `js/sync-firestore.js` function header verbatim: "Native CAS parity is a documented follow-up; web-only in E-1b." (4) Sign-off checklist item: implementer files a follow-up tracking issue (or adds a TODO comment in `sync-firestore.js`) so the native parity work is queued before E-3 listeners ship. |
| **Dispatcher aborts entire loop on first per-store throw** | low | data-correctness (cross-store) | If `_runMergeCycle` doesn't wrap each `module.merge()` in try/catch, the first stub's `throw new Error('not implemented')` would abort the loop and skip subsequent stores. In E-1b this is harmless (all 4 throw), but the contract for E-1c/d/e is that one buggy merge function can't take down the cycle. **Mitigation:** Per-store try/catch is a hard requirement in this audit — test case explicitly: "dispatcher invokes all 4 stub merge functions even when the first throws"; assert all 4 modules' `merge()` got called (mock with a spy counter); assert `emit('merge-error', ...)` fired 4 times; assert `emit('merge-cycle-complete', ...)` fired once with `storeResults` showing 4 failures. |
| **Boot regression — non-default flag value mutates boot path** | low | local-only | The new `tempo_sync_steady_state_enabled` localStorage flag must be byte-identical to "absent" when the value is anything other than `'1'`. If the implementer reads it as `Boolean(localStorage.getItem(...))`, then `'0'` would coerce to `true` (non-empty string). **Mitigation:** Per Pick C on TODO #4 explicitly: gate must be `ls.getItem(STEADY_STATE_ENABLED_KEY) === '1'`. Test case: "startSteadyState() is a no-op when flag is absent" (default boot path); "startSteadyState() is a no-op when flag is '0'"; "startSteadyState() is a no-op when flag is 'true'" (no string coercion). Sign-off checklist item: implementer verifies pre-E-1b boot is byte-identical via the manual procedure below. |
| **Interval clamp boundary off-by-one** | low | low (poll-frequency drift) | If the clamp uses strict `<` instead of `<=` at `STEADY_STATE_MIN_MS` (10000) or `STEADY_STATE_MAX_MS` (600000), boundary values fail silently and the timer falls back to the default. **Mitigation:** `Math.min(MAX, Math.max(MIN, value))` is the inclusive form. Test cases: "interval = 10000 → 10000 (boundary inclusive)"; "interval = 600000 → 600000 (boundary inclusive)"; "interval = 9999 → 10000 (clamped to MIN)"; "interval = 600001 → 600000 (clamped to MAX)"; "interval = 'abc' → 30000 (NaN falls back to default)"; "interval = '' → 30000 (empty string parses to NaN)". |
| **`visibilitychange` listener leak on stopSteadyState()** | low | low (memory) | If `stopSteadyState()` uses `document.removeEventListener('visibilitychange', someInlineFunction)`, removal fails because the original `addEventListener` reference was a different function. Listener accumulates across start/stop cycles → memory leak + duplicate timer ticks. **Mitigation:** The implementer MUST stash the handler on `_steadyVisibilityHandler` (module scope) so `removeEventListener` references the SAME function. Same pattern for `_steadyNetworkUnsubscribe` (the return value of `Platform.network.onChange` if it returns an unsubscribe function — feature-detect via `typeof unsub === 'function'`). Test case: "calling startSteadyState() then stopSteadyState() leaves zero listeners on document" — verify via a spy on `addEventListener` and `removeEventListener` counting same-handler-reference pairs. |
| **`sw.js` CACHE_NAME bump missed** | low | web-bytes | The PR ships changes to 4 cached web files (`js/sync-engine.js`, `js/sync-firestore.js`, plus 4 new files added to `ASSETS`, plus the `index.html` script-tag additions). All trigger the repo cache-bump rule. If `CACHE_NAME` isn't bumped, existing PWA installs serve stale pre-E-1b code from `caches.match` until the SW expires. **Mitigation:** Bump from `'stopwatch-v74-e1a-test-harness-fix'` → `'stopwatch-v75-e1b-steady-state-scaffold'` in the same PR. Sign-off checklist includes a dedicated bump-verification item. The orchestrator's pr-shipper handles this via the `engine-implementer reports sw.js cache-bump needed: yes` signal — which fires because cached web files (`js/sync-engine.js` et al.) change. |
