## Goal

Land the second per-store merge function (history) so the dispatcher transitions from "real × 1 + stub × 3" to "real × 2 + stub × 2". The history merge function (Pick B on TODO #1 — sessions only) is self-contained: takes the local snapshot (currently null — dispatcher passes null today; merge fn reads fresh via `History.getSessions()`), calls `SyncFirestore.getCollection('users/{uid}/history')` internally, pre-filters future-schema records (Pick A on TODO #3 — `Schema.isFutureRecord(rec)` per-record skip + `skipped++` + warning), unions cloud ∪ local sessions, dedupes by `id` per F2 (cloud-wins on collision matching D-1 precedent), applies **record-level LWW** to the session envelope (incl. `note` and `tags`) using `updatedAt` since `js/history.js` does NOT stamp `noteUpdatedAt` / `tagsUpdatedAt` today (TODO #2 finding — see audit note below), dedupes nested `phaseLog` entries by `(deviceId, phaseStartedAt)` per F6 (A-1 stamped these at all four push sites), writes merged sessions back via `SyncFirestore.runTransaction` per-record with `Schema.stamp(session)` (E-1b CAS enforces F19a refuse-writeback at write time), and returns `{ ok, count, skipped, remoteArrivals: {}, warnings }`. **No F15 emit** (Pick B on TODO #4 — sessions arrivals are silent; the only F15 surface remains `meds-arrival`). The dispatcher's F13 flip (E-1c-shipped) wraps the cycle, so E-1d does NOT modify `sync-engine.js`. New test file `tests/sync-merge-history.test.js` (Pick A on TODO #6) ships 12-15 cases covering the F2 / F6 / F10 / F13 / F19a layers plus idempotency + CAS abort tolerance.

## Risks

| Risk | Likelihood | Blast radius | Mitigation |
|------|------------|--------------|------------|
| **Cloud history snapshot is large (months of usage → IDB-backed; 1000+ sessions plausible)** | med | data-correctness (med — memory pressure + slow cycle) | A power user with 6+ months of Pomodoro / Flow / Cooking usage can easily accumulate 1000+ sessions. Loading all of them into a single `mergedById` Map + running per-record CAS writeback serially could take 30s+ on a slow connection and bloat WebView memory. Firestore's `getCollection` returns all docs in one shot today (the SDK wrapper doesn't paginate). **Mitigation:** (1) The CAS writeback loop is per-record; each `runTransaction` is independent — slow cycles don't corrupt anything, they just take time. (2) The dispatcher's `_steadyRunInFlight` re-entry guard ensures cycle N+1 returns immediately if cycle N is still running — no overlapping reads. (3) Pagination + cursor-based reads land in **E-3** (real-time listeners) or as a follow-up if the perf bites; E-1d ships the correct algorithm and accepts the perf risk for the typical user. (4) Test case #12 (`large cloud snapshot`) exercises 50+ sessions to assert correctness — perf is observed but not asserted. (5) Document the gap in the return summary so engine-tester surfaces it manually on real-world data. |
| **Session `id` collision (F2 says unique, but defensive) — different content under same id** | low | data-loss (med — one side's record overwritten) | F2's `${deviceId}-${Date.now()}-${counter}` shape is engineering-zero collision in practice (deviceId is UUID v4 + per-device monotonic counter). But the union step still has to pick a winner if two records carry the same id with different content. **Mitigation:** cloud-wins on `cloudAt >= localAt` LWW tie (matches D-1 reconcile precedent + E-1c meds metadata LWW pattern). On strict equality, cloud's record is canonical because the cloud's record went through CAS-mediated writeback by some device — local's record may be the same record loaded mid-flight. Test case #2 (`cloud-wins on id collision`) asserts this. |
| **Record-level LWW on note/tags causes stale-overwrites-fresh edits** | med | data-loss (med — UX paper cut) | Without per-field stamping (TODO #2 finding: A-1 only stamped record-level), if Device A edits a tag and Device B edits the note within the same merge cycle window, the device with the older `updatedAt` LOSES its edit on the next push. Example: Device A adds tag at T=100 → `updatedAt=100`. Device B edits note at T=110 → `updatedAt=110`. Cloud sees both; B wins; A's tag is lost. **Mitigation:** (1) **This is documented behavior under Pick B on TODO #2 — Kyle accepted the trade.** Per-field stamping ships in a follow-up PR. (2) The window is small in practice — steady-state merge interval is 30s default; same-session simultaneous edits across two devices are uncommon. (3) Test case #3 (`note LWW`) + #4 (`tags LWW`) both assert the record-level behavior so the regression is caught if the implementer accidentally introduces per-field comparison. (4) Document the gap in the PR description so future per-field-stamping PR has a known precedent to cite. |
| **`phaseLog` dedup key — A-1 stamping incomplete or missing at some push site** | low | data-correctness (med — phaseLog duplicates in synced Pomodoro sessions) | The dedup tuple `(deviceId, phaseStartedAt)` only works if every push site stamps both fields. A-1 audit confirmed four sites (3 in `pomodoro.js` + 1 in `pomodoro-ui.js`); the auditor re-verified via grep — all four carry `deviceId` + `phaseStartedAt` per A-1's contract. **Mitigation:** (1) Test case #5 (`phaseLog dedup by (deviceId, phaseStartedAt)`) builds two phaseLog arrays from a cross-device Pomodoro session, unions them, asserts the duplicate collision pair collapses to 1. (2) Test case #5 sub-case: legacy phaseLog entries (no `deviceId`) fall back to `phaseStartedAt`-only matching — assert these survive verbatim (F19b spirit). (3) If a follow-up PR adds a fifth `phaseLog.push` site (e.g., Flow's hypothetical phaseLog), the stamping has to land alongside the push — F6 is an engine-level contract, not a sync-layer concern. |
| **CAS write loop is non-atomic across multiple sessions — partial cloud state on failure** | med | data-correctness (med — convergence delayed, not corrupted) | If session #1's CAS succeeds and session #2's CAS rejects (network or refuse-writeback), the cloud has session #1's new state but not session #2's. On retry next cycle, the merge function fetches cloud again — session #1 is canonical, session #2 falls through reconcile + retries. **This is the documented Firestore CAS pattern, not a bug.** Mitigation: (1) Per-session try/catch around each `runTransaction` invocation — one failure must NOT skip subsequent sessions (Risk #6 inherited from E-1c). (2) Count per-session skips into `result.skipped`; surface to `merge-cycle-complete` consumer for visibility. (3) Test case #10 (`CAS abort tolerance`) asserts loop continues after one rejection. (4) Idempotency (Risk #6 below) guarantees retry convergence. |
| **F19a per-record pre-filter inverts logic and skips current-schema records** | low | data-loss (high — current-schema records dropped from merge) | Same risk as E-1c Risk #4. If the pre-filter is `if (data.schemaVersion <= Schema.SCHEMA_VERSION) { skipped++; continue; }` (inverted), it skips all current/past records and ingests ONLY future ones. **Mitigation:** mandate use of `Schema.isFutureRecord(data)` — NOT a hand-rolled comparison. Test case #6 (`F19a future-record pre-filter`) asserts current-schema records pass through and future-schema records are skipped. |
| **Idempotency broken — running the same merge twice produces duplicate writeback** | low | data-correctness (low — convergence wastes writes) | If the merge function unconditionally writes every merged record back regardless of whether it matches the cloud's current state, every cycle generates N writes for N sessions — bloating Firestore writes + costing bandwidth. The CAS gate prevents corruption but doesn't prevent wasted writes. **Mitigation:** (1) Per-record `Schema.stamp(session)` is observably a no-op when the record is byte-identical to cloud's current. (2) The merge function does NOT bump `session.updatedAt` (it preserves the LWW winner's value), so identical records stay identical. (3) Test case #9 (`idempotency`) asserts the 2nd merge with the same cloud state produces 0 NEW writes that move the on-disk state — `runTransaction` is still called but each callback's `tx.set` is observable as a no-op via the test spy. |
| **F13 write gate inherited from E-1c — no new wiring needed** | low | data-correctness (low — defensive verification) | E-1c shipped the dispatcher-wide `SyncState.set('hydrating')` flip in `_runMergeCycle` at lines 1543-1559. E-1d's merge function runs INSIDE the already-flipped window; it MUST NOT touch `SyncState` (the dispatcher owns the gate). **Mitigation:** Test case #7 (`F13 gate during cycle`) asserts `SyncState.get() === 'hydrating'` mid-cycle; Test case #8 (`F13 gate releases`) asserts `SyncState.get() === 'ready'` after the cycle resolves. Both cases exercise the dispatcher's contract, not the merge function's internal logic. |
| **Cache bump rule (`sw.js` v76 → v77)** | low | web-bytes | E-1d modifies one cached web file (`js/sync-merge-history.js`). Without a `CACHE_NAME` bump from `'stopwatch-v76-e1c-meds-merge'` to `'stopwatch-v77-e1d-history-merge'`, existing PWA installs serve stale pre-E-1d code from `caches.match` until the SW expires. **Mitigation:** the affected-files table mandates the bump in the same PR. Sign-off checklist item below dedicates a row to verification. The orchestrator's `pr-shipper` enforces via the engine-implementer's report. |
