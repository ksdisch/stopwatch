## Goal

Land the first real per-store merge function (meds) so the dispatcher built in E-1b transitions from "exercise-able stub loop" to "stub × 3 + real merge × 1". The meds merge function (Pick A on TODO #1) is self-contained: takes the local snapshot, calls `SyncFirestore.getCollection('users/{uid}/meds')` internally, pre-filters future-schema records (Pick C on TODO #5 — increment `skipped`), iterates each med, calls D-2's `MedsManager.reconcileDoseLog(med, incoming)` to collapse ±15-min cross-device duplicates + clamp clock-skewed entries (F1 + F16), assigns the result onto `med.doseLog`, fires `MedsManager.onMergeComplete(medId)` to re-derive `lastTakenAt` (F4), counts NEW remote arrivals per-med, writes the merged record back via `SyncFirestore.runTransaction` (the CAS gate enforces F19a refuse-writeback at the record level), and on any med with ≥2 NEW remote entries emits `meds-arrival` (F15). The dispatcher in `_runMergeCycle` flips `SyncState` to `'hydrating'` before the per-store loop and back to `'ready'` after (Pick B on TODO #2 — dispatcher-wide flip; F13 contract). D-1's `reconcileImportedBucket` at the comment seam gets the same 5-6 line reconcile loop in-place (Pick A on TODO #4 — no shared helper extraction). New test file `tests/sync-merge-meds.test.js` (Pick A on TODO #6) ships ~12-15 cases covering the F1/F4/F13/F14/F15/F16/F19a layers plus idempotency.

## Risks

| Risk | Likelihood | Blast radius | Mitigation |
|------|------------|--------------|------------|
| **Merge cycle leaves `SyncState` stuck in `'hydrating'` if an exception escapes the dispatcher** | low | **data-correctness (HIGH — permanent write block)** | If the F13 flip is written as `set('hydrating'); …loop…; set('ready');` without a `try/finally`, a throw in the loop body (or worse, in the `emit('merge-cycle-complete')` call) leaves `SyncState === 'hydrating'` until the user reloads. Every local engine write through `SyncState.canWrite()` would then be blocked silently. **Mitigation:** the implementation MUST wrap the dispatcher's per-store loop in `try { … } finally { SyncState.set('ready'); _steadyRunInFlight = false; }`. The existing `_steadyRunInFlight` reset at line 1563 moves into the same `finally`. Test case (#9 below): "F13 gate releases on exception" — mock one merge function to throw a non-Error value; assert SyncState ends at `'ready'` and `_steadyRunInFlight` is `false`. |
| **CAS write loop is non-atomic across multiple meds — partial cloud state on failure** | med | data-correctness (med — convergence delayed, not corrupted) | If med #1's CAS succeeds and med #2's CAS rejects (network or refuse-writeback), the cloud has med #1's new state but not med #2's. On retry next cycle, the merge function fetches cloud again — med #1 is already canonical, med #2 falls through reconcile + retries. **This is the documented Firestore CAS pattern, not a bug.** Mitigation: (1) per-med try/catch around each `runTransaction` invocation — one failure must not skip subsequent meds (E-1c's loop must NOT short-circuit on first error). (2) Count per-med skips into `result.skipped`; surface to `merge-cycle-complete` consumer for visibility. (3) Test case (#8 below): "CAS abort on stale schemaVersion" — mock `tx.refuseWriteback` to throw `kind: 'refuse-writeback'`; assert merge function continues to the next med + increments `skipped`. (4) Idempotency invariant (Risk #7) guarantees the retry next cycle converges. |
| **F15 false positives — same-device retry counted as NEW remote arrival** | med | low (toast UX noise) | If "NEW remote" is computed as `entry.deviceId !== localDeviceId` without ALSO checking "did not exist in local doseLog before this merge", a same-device re-push (e.g., transient network retry from this very device's earlier uploader) would be counted as remote because the wire-format envelope has its own `deviceId`. Wait — same-device retries have `deviceId === localDeviceId` by definition, so the `!==` check excludes them. The actual false-positive vector is: cross-device entry that already existed in local doseLog (e.g., a previous merge cycle ingested it) — counting it again on the next cycle would double-count. **Mitigation:** the `newRemoteCount` predicate must check `!beforeMerge.some(le => le.deviceId === e.deviceId && le.takenAt === e.takenAt)` where `beforeMerge` is a snapshot of `med.doseLog` captured BEFORE `result.entries` is assigned. Test cases (#7 idempotency + #1 happy path) catch this — 2nd merge cycle with same cloud state must produce 0 F15 emits. |
| **F19a pre-filter inverts logic and skips current-schema records** | low | data-loss (med — current-schema records dropped from merge) | If the pre-filter is `if (data.schemaVersion <= Schema.SCHEMA_VERSION) { skipped++; continue; }` (inverted comparison), it would skip ALL current and past records, ingesting ONLY future ones — the exact inverse of the intent. The correct check is `Schema.isFutureRecord(data)` — already a helper, already used elsewhere. **Mitigation:** mandate use of `Schema.isFutureRecord(data)` (NOT a hand-rolled comparison). Test case (#5 below): "F19a per-record skip — current-schema records pass through; future-schema records are skipped + counted." |
| **D-1 reconcile retrofit changes existing reconcile flow's behavior** | low | data-correctness (med — affects the imported-bucket reconcile path) | The comment seam at `js/sync-engine.js:1278-1286` documents what to do, but the surrounding flow (`_mergeMeds` at 1277, `_mergeRestLog` at 1287) has been running in production without the reconcile loop since D-1 shipped. Replacing the comment with a real loop means D-1's `reconcileImportedBucket` NOW collapses ±15-min cross-device duplicates that previously survived. Users mid-Stage-D handoff between PRs would see a behavior change. **Mitigation:** (1) the change matches the comment seam's documented intent verbatim; D-2's brief explicitly defers the wire-up to E-1c (line 40 of D-2-AUDIT). (2) The reconcile is purely additive — collapsing duplicates is the desired behavior; the only "regression" is the absence of duplicates that should have never persisted. (3) Test case (#12 below): "D-1 reconcile retrofit collapses cross-device duplicates" — feed `reconcileImportedBucket` a mergedMeds with a known F1 duplicate pair (deviceId A + deviceId B within 15min); assert post-reconcile `med.doseLog.length === N - 1`. |
| **Cache bump rule (`sw.js` v75 → v76)** | low | web-bytes | E-1c modifies two cached web files (`js/sync-engine.js`, `js/sync-merge-meds.js`). Without a `CACHE_NAME` bump from `'stopwatch-v75-e1b-steady-state-scaffold'` to `'stopwatch-v76-e1c-meds-merge'`, existing PWA installs serve stale pre-E-1c code from `caches.match` until the SW expires. **Mitigation:** the affected-files table mandates the bump in the same PR.
