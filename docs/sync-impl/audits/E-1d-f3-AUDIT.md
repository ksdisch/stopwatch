## Goal

Land F3 BFRB stream consolidation end-to-end in one PR: a new `js/bfrb-events.js` module owns the consolidated `bfrb_events` localStorage store and ships a phased one-way migration that unions the three legacy keys into a single tagged stream (entries gain `context: 'global' | 'flow' | 'pomodoro'` + flat optional sub-fields `sessionId?` / `phase?` / `cycleIndex?` per Pick A on TODO #3 — `timestamp` is renamed to `takenAt` to match D-2's doseLog convention), every write is stamped via `Schema.stamp(entry)` (F10) and gated through `SyncState.canWrite()` (F13), and the migration marker `tempo_bfrb_events_migration_v1='1'` guarantees idempotency across re-boots. The four UI surfaces that previously read 1-of-3 legacy keys (`js/global-bfrb.js` FAB count, `js/flow-ui.js` session counter, `js/pomodoro-ui.js` session counter, `js/analytics.js` 14/30/90-day trend rollup) all switch to read from `BfrbEvents.*` with byte-equivalent output on first load. Sync wiring lands at the same time per Pick A on TODO #4 — `bfrb_events` is added as the 5th `SYNCED_STORES` entry and a new `js/sync-merge-bfrb.js` ships the per-store append-merge dedup by `(deviceId, takenAt)` so cross-device catches converge. Two new test files cover the surface — `tests/bfrb-events.test.js` for migration + module API and `tests/sync-merge-bfrb.test.js` for the per-store merge — pushing the baseline from 454 to ~468-476.

## Risks

| Risk | Likelihood | Blast radius | Mitigation |
|------|------------|--------------|------------|
| **Migration corrupts BFRB history — bad legacy entry shape lands in `bfrb_events` malformed** | med | data-loss (med — analytics undercounts post-migration) | The three legacy keys have slightly different entry shapes (`bfrbs_global` is `{ timestamp }`; `flow_bfrbs` is `{ timestamp, phase }`; `pomodoro_bfrbs` is `{ timestamp, phase, cycleIndex }`) but could contain pre-schema legacy entries with missing `timestamp` (the `js/global-bfrb.js:86-89` filter already skips these in `countForLabel`). If the migration treats malformed entries as valid, bad data enters `bfrb_events` and downstream `countToday` / analytics rollups skew. **Mitigation:** per-entry try/catch in the migration union step; require `typeof e.timestamp === 'number'` before mapping to `takenAt`; skipped entries push a warning + increment a migration-local counter (logged once at the end of the union). Test case `migration skips malformed entries` codifies this. |
| **Migration runs twice and creates duplicates** | med | data-correctness (high — analytics double-counts everything) | If the marker write fails (storage quota, browser eviction) between the `bfrb_events` write and `setItem(marker)`, the next boot re-runs the migration. Re-reading the legacy keys (still on disk per Pick B) PLUS the already-written `bfrb_events` could produce double entries. **Mitigation:** write `bfrb_events` FIRST, then set marker; if marker write fails, the next boot's re-union takes the same 3 legacy keys as input AND dedups by `(deviceId, takenAt)` defensively — output is byte-identical, so the re-run is observably a no-op. Test case `migration idempotency — re-run produces identical output` codifies this. Additional mitigation: marker check happens BEFORE union runs, so if the marker IS set we skip union entirely (cheap path). |
| **UI reads break post-migration — Flow / Pomo / FAB / Analytics show 0 or stale counts** | med | UX-bug (med — user sees their BFRB tally vanish for a day) | All 4 surfaces previously read 1-of-3 legacy keys directly via `JSON.parse(localStorage.getItem(...))`. Post-migration they read `BfrbEvents.*`. If the migration leaves `bfrb_events` empty (e.g., all three legacy keys were empty + marker is set) the UI legitimately shows 0; but if the migration silently fails midway and marker is set anyway, the UI shows 0 even though the legacy keys have data. **Mitigation:** (1) Migration is atomic in the sense that `bfrb_events` is written BEFORE the marker is set — partial state ends up with no marker, so next boot re-runs and self-heals. (2) Phase 4 ui-wirer visually verifies all 4 surfaces post-migration on `localhost:8765` with a pre-seeded fixture (legacy entries in all 3 keys → reload → verify FAB count + Analytics 14-day trend match the legacy union). (3) Test case `getByContext + countToday output byte-equivalent to legacy reads` codifies this. |

The two paths MUST produce identical `stamps[]` arrays for the same input data. Engine-tester confirms manually: with the dev flag on, `localhost:8765` console output shows 5 merge-cycle events. |
