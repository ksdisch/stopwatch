# PR S0-1 — Stage 0: Firebase project config + plugins + security rules

**PR:** `feat/sync-stage-0-firebase-setup` → `main`
**Scope:** Land Firebase project config files, Capacitor + JS SDK plugins, initial Firestore security rules, and a Firebase setup guide. **No behavior change.** Web boot stays byte-equivalent; iOS still builds; `tempo_sync_enabled` stays off.
**Status:** Audit-only commit. The branch's first commit is this doc plus `docs/sync-impl/FIREBASE-SETUP.md`. The code commit (config + plugin install + rules) follows after the user creates the Firebase project in the console and pastes real config values.

This audit enumerates every file the code commit will touch, calls out the two-commit plan the brief mandates, and surfaces the manual setup the user performs in the Firebase Console between commit 1 and commit 2.

Land the Firebase / Firestore backend's static plumbing — npm + CocoaPods plugins, `firebase.json` / `firestore.rules` / `firestore.indexes.json`, the public web config snippet, and the iOS `GoogleService-Info.plist` — so subsequent PRs (B-1 SyncEngine scaffold, B-2 auth, B-3 uploader) can wire against a real backend. This PR ships zero runtime behavior: `js/sync-firebase-config.js` is committed but NOT loaded from `index.html` (B-2 wires it in behind `tempo_sync_enabled`).

**Per-user isolation contract introduced by `firestore.rules`:** All sync paths live under `users/{uid}/...`; `request.auth.uid == userId` is the only access predicate. This isn't an F-numbered invariant in `CLOUD-SYNC-STRATEGY.md`, but it's the security contract that makes every future synced-record write safe: a write that doesn't carry the correct authenticated UID is denied by the server. This is the only enforcement S0-1 ships — every other invariant (LWW, append-merge, CAS, schemaVersion) lives in client code that hasn't been written yet.

**No re-implementation risk in this PR.** `escapeHtml`, `Utils.formatMs`, `Platform.haptic`, `Platform.notify`, and `js/schema.js` stamping helpers are all client-side concerns that S0-1 doesn't touch. The sign-off checklist below marks these N/A.

## Manual setup steps

**This PR's defining characteristic: most of the work happens in the user's browser, not in code.** S0-1 ships as a two-commit PR with a hard stop between commits so the user can create the Firebase project and paste real config values before any code ships.

### Two-commit plan (mandated by `S0-1-PROMPT.md`)

1. **Commit 1: `docs(sync-impl): S0-1 audit + Firebase setup guide`**
   - Files: `docs/sync-impl/audits/S0-1-AUDIT.md` + `docs/sync-impl/FIREBASE-SETUP.md`.
   - Branch: `feat/sync-stage-0-firebase-setup`.
   - **STOP after this commit.** Push the branch, open a draft PR, wait for the user to perform the six manual setup steps below.
2. **Commit 2: `chore(sync): Firebase project config + plugins (S0-1)`**
   - Files: `package.json`, `package-lock.json`, `capacitor.config.json`, `ios/App/App/GoogleService-Info.plist`, `ios/App/Podfile`, `firebase.json`, `firestore.rules`, `firestore.indexes.json`, `js/sync-firebase-config.js`, `.gitignore`.
   - **Only runs after the user has:** (a) created the Firebase project, (b) registered the iOS app + downloaded `GoogleService-Info.plist`, (c) registered the web app + provided the public config snippet for `js/sync-firebase-config.js`. The user pastes these values into a comment on the draft PR or hands them to the implementer directly.
   - PR title once both commits land: `chore(sync): Firebase project config + plugins (S0-1)`.

### Six manual steps the user performs in the Firebase Console (between commit 1 and commit 2)

These mirror the six steps in `PLAN.md` § "Backend setup (Firebase project)" — restated here with concrete URLs, exact names, and the gotchas already known from `BACKEND-SELECTION.md`.

1. **Create the Firebase project.** Go to https://console.firebase.google.com → "Add project". Name: `tempo-sync` (or similar — name is changeable, project ID is not). Decline Google Analytics (not needed, adds another consent surface). After creation, **immediately go to Project Settings → General → "Default GCP resource location"** and pick `us-central1`. **THIS REGION IS PERMANENT.** Per `BACKEND-SELECTION.md` § "Gotchas": "Database region is permanent. Pick `us-central1` or `nam5` once and you're stuck." `us-central1` is the recommendation.
2. **Enable Firestore.** Build → Firestore Database → "Create database". Select **Production mode** (denies everything by default — security rules from `firestore.rules` will replace this on first `firebase deploy`). Location: should auto-select to match the project's GCP resource location (`us-central1`). If a region picker appears, pick `us-central1`. Confirm.
3. **Enable Authentication → Google sign-in provider.** Build → Authentication → "Get started" → Sign-in method tab → Google → Enable. Project support email: `kstan.disch@gmail.com`. Save. Under the same Auth section, go to Settings → Authorized domains → add `ksdisch.github.io` (production web) and confirm `localhost` is already in the list (Firebase adds it by default for local dev).
4. **Register the iOS app.** Project Settings → General → "Your apps" → tap the iOS+ button. Bundle ID: `com.ksdisch.tempo` (must match `capacitor.config.json`'s `appId`). App nickname: `Tempo iOS`. App Store ID: leave blank for now. Click "Register app" → **download `GoogleService-Info.plist`** and save to the local clone at `ios/App/App/GoogleService-Info.plist`. Skip the "Add Firebase SDK" and "Add init code" steps in the console wizard — those are for non-Capacitor apps; we get the SDK via the npm plugins.
5. **Register the web app.** Same screen → tap `</>` (web). App nickname: `Tempo Web`. Do NOT enable Firebase Hosting (we deploy via GitHub Pages). Click "Register app" → **copy the `firebaseConfig` JS object** from the console and either paste it into a draft-PR comment for the implementer, or paste directly into `js/sync-firebase-config.js` (commit 2). The object contains `apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId`, `appId`. All public — safe to commit.
6. **Set a $1/mo budget alert.** Open https://console.cloud.google.com/billing → select the project (Firebase auto-creates a GCP project under the hood) → Budgets & alerts → Create budget. Amount: `$1.00`. Threshold rules: 50%, 90%, 100% (default). Email alerts to `kstan.disch@gmail.com`. **Why $1:** Spark plan is free at our scale (per `BACKEND-SELECTION.md`: 2000× headroom on writes), so a $1 trip-wire signals something unexpected (a runaway client, a credential leak, etc.). Per `PLAN.md`: "Spark plan can be paused on quota overrun; budget alert is the early-warning."

### After the user finishes the six steps

The user signals greenlight (in the draft PR or in chat). The implementer then:

1. Pastes the web config snippet into `js/sync-firebase-config.js` (or wires up whatever the user provided).
2. Places `GoogleService-Info.plist` at `ios/App/App/GoogleService-Info.plist`.
3. Runs `npm install firebase @capacitor-firebase/authentication @capacitor-firebase/firestore`.
4. Runs `npx cap sync ios` to update `ios/App/Podfile`.
5. Writes `firebase.json`, `firestore.rules`, `firestore.indexes.json` per the shapes in the Affected files table above.
6. Updates `capacitor.config.json` with the `plugins` block.
7. Updates `.gitignore` with the service-account ignores.
8. Verifies the six manual checks in the Test scope section.
9. Commits commit 2 + pushes + flips the PR out of draft.
