## 2. The why

**Why noise-color theory matters here.** Kyle's reference channel (Otto's Healing Sounds) sells green noise, brown noise, pink noise, etc. — long-form ambient soundscapes. "Add Otto's videos" was an option (YouTube IFrame embed), but procedural synthesis covers ~80% of the listening experience with zero ToS surface, zero hosting cost, zero offline-storage hit. Each "color" is just white noise pushed through a different filter. Once you have a single-buffer Web Audio pipeline (which PR #82 already built), adding a new color is ~15 lines of filter math. Rejected alternative: bundling royalty-free MP3 loops — adds ~5–15 MB to the install per loop, and the cache-management surface for offline-playable files is real overhead.

**Filter implementations chosen, with tradeoffs.** Green = 2-pole resonant biquad bandpass at 500 Hz, Q=1.0 (Robert Bristow-Johnson's audio EQ cookbook formula — the canonical recipe). Blue = single-difference differentiator (`y[n] = x[n] - x[n-1]`), which is technically a +6 dB/oct slope rather than the textbook +3 dB/oct definition of blue noise; the half-differentiator that gives a true +3 dB/oct is much hairier to implement and the single-difference version is what most procedural-noise tutorials ship as "blue." Violet = differentiator applied twice (second-difference). Gray = Paul Kellet pink (already in the file) fed through a 2 kHz notch — approximates A-weighting's inverse (the "U-shape" that compensates for human auditory sensitivity), much simpler than a real A-weighting biquad chain. **Pattern: ship recognized-good-enough approximations and validate by ear; reach for the mathematically-pure version only if the approximation is perceptually wrong.**

**Why the per-color amplitude scalars matter more than the filter math.** White, brown, pink were already amplitude-tuned to be subjectively level-matched at the same `ambient_volume = 0.05` default (pink's `* 0.11` scalar in the existing code was the tuning target). Each new color needed its own scalar: green `* 4.0` (bandpass output is dim), blue `* 0.5` (differentiator is bright), violet `* 0.25` (steeper HF slope is brighter), gray no extra scalar (notch barely changes power). Got these first-pass by reading the existing pink scalar and guessing relative loudness; held up under Kyle's smoke. **Pattern: the smoke validates loudness; the engine commits to math, not TODOs.**

**Why PR #89 skipped the orchestrator.** The orchestrator workflow is 5 phases × subagent dispatches × audit + pause checkpoints. Worth it for engine work that touches risk surfaces (sync invariants, schema migrations, native bridges). For a pure-UI follow-up — 3 files, no engine, no tests, ~30 lines of wiring against APIs that already existed and were tested in PR #88 — the overhead is the entire ship. Went direct: code → kapture smoke → branch → commit → push → PR. Got pushback from a Stop-hook for proposing "should I open this as a follow-up PR?" instead of just doing it; useful correction. **Pattern: the orchestrator is for institutional traceability on risky changes, not a mandatory liturgy for every PR.**

**Why persist the drawer profile, why auto-resume.** First version of PR #89 was "drawer is live-only — controls THIS session, doesn't persist." Kyle smoked it, immediately flagged the asymmetry: "volume remembers, profile doesn't." Real UX bug, not design. Persistence shipped in `cee1353`. Then a second asymmetry surfaced: even with the dropdown remembering the pick, the sound itself didn't auto-resume on refresh because Web Audio's `AudioContext` is gesture-gated — the browser silently suspends any audio until the user has interacted with the page. Auto-resume shipped in `a219939` via a one-shot document-level click+keydown listener that claims the first gesture as the resume trigger. Race-guarded against the Flow/Pomodoro Start button (which also calls `startAmbient` synchronously) by checking `SFX.getAmbientProfile()` in the bubble phase — if the engine already has a profile, the hook is a no-op. **Pattern: Web Audio's user-gesture constraint is the load-bearing API rule; anywhere ambient could need to start without a button-press, you need a gesture-claiming hook.**

**Why "stacked PR" for #89.** PR #89's dropdown lists all 8 colors. The 4 new colors only existed on the `feat/ambient-colors-expand` branch (PR #88) when I started #89. Options: (a) wait for #88 to merge, (b) branch from main and only include the 3 pre-PR-88 colors then follow up after #88 merges, (c) branch from #88's branch and target it as the PR base. Picked (c) — GitHub handles the rebase automatically once #88 merges into main; the merge target gets switched silently. Kyle merged #88 mid-session, so by the time we wrapped, PR #89 was already targeting main without manual intervention.

## 3. Concepts and vocabulary

- **Web Audio noise colors (general)** — synthetic noise where the power spectrum's slope is shaped by a filter. White (flat), pink (−3 dB/oct), brown/red (−6 dB/oct), blue (+3 dB/oct), violet/purple (+6 dB/oct), gray (perceptually-flat U-shape via A-weighting). Procedural — generated sample-by-sample, no audio files needed. (Lives in `js/audio.js:_generateAmbientBuffer`.)
- **RBJ biquad / Robert Bristow-Johnson's audio EQ cookbook** — the canonical formula set for IIR filter coefficient calculation in audio code: bandpass, notch, peaking, shelf, etc. parameterized by center frequency `f0`, sample rate, Q. If you're writing a filter in audio code, you almost certainly want these coefficients. (Used for green's bandpass at 500 Hz and gray's notch at 2 kHz.)
- **Differentiator filter** — `y[n] = x[n] - x[n-1]`. Trivial IIR; produces a +6 dB/oct slope (HF boost). Used for blue noise procedurally; the second-difference form (`x[n] - 2*x[n-1] + x[n-2]`) produces violet.
- **A-weighting** — IEC-standard frequency response curve that approximates human auditory sensitivity (~peak at 2–4 kHz, rolloff at low and high ends). Multiplying audio by A-weighting gives "perceived loudness." Gray noise = inverse-A-weighting filter on white noise → perceptually flat across the audible band.
- **`AudioBufferSourceNode` with `loop = true`** — Web Audio pattern for seamless ambient playback. Pre-generate one buffer (5 seconds here, ~880 KB at 44.1 kHz mono), play through a looped source, route through a `GainNode` for volume. Cheaper than ScriptProcessorNode and doesn't fight the deprecation path. Existing pattern from PR #82, unchanged this session.
- **User-gesture requirement (Web Audio)** — modern browsers suspend `AudioContext` until the page receives a real user interaction (click, keypress, touch). Any audio code that tries to start before the first gesture silently no-ops. The mitigation we shipped: a one-shot document-level listener that claims the first gesture as the audio-resume trigger.
- **Service worker cache invalidation** — `sw.js` precaches a list of static assets under a versioned `CACHE_NAME`. When `CACHE_NAME` bumps, the install handler populates the new cache; the activate handler deletes any cache where `key !== CACHE_NAME`. `skipWaiting()` + `clients.claim()` make the new SW active immediately. Forgetting to bump means existing PWA installs serve stale JS indefinitely — the "cache-bump trap" the audit flagged today.
- **Bubble-phase event listener** — when you attach `addEventListener` without `{ capture: true }`, your handler runs after the target element's own handler has bubbled up. Useful for "claim the first gesture, but only if the target's own logic didn't already handle it" patterns — like our auto-resume hook checking whether Flow.start already set the ambient profile.
- **One-shot listener pattern** — listener removes itself in its own callback before doing the work. Cleaner than `{ once: true }` when you need to remove multiple listeners that should all fire-or-not-fire as one group (as in our `click` + `keydown` pair both pointing at `onFirstGesture`).
- **Tier-gated PR ship (orchestrator)** — Phase 5's behavior switch: low → auto-push + auto-PR. Medium → 30s proceed-by-default window. High → pause for "ship it" approval. The `sw.js` cache bump alone forces medium per the rubric. Today's PR #88 was medium; PR #89 bypassed the orchestrator entirely.
- **Stacked PRs** — feature branch B targets feature branch A (instead of main). GitHub auto-rebases B's PR onto main once A merges. Lets you ship a follow-up before the dependency lands. Today: PR #89 stacked on PR #88's branch so the new dropdown could reference all 8 colors.

## 4. Takeaways

- **API reality-check before scope-locking a brief.** Today's audit caught two stale assumptions in my brief: `sw.js` CACHE_NAME current value was off-by-one (assumed PR #86 had merged; it hadn't), and the `<option>` order ambiguity (brief gave two contradictory orderings). Both would have been caught later in the diff anyway, but the audit-before-code pause is what makes the catch cheap rather than a re-roll. **Rule:** if a brief asserts "current value is X," verify against the file system before treating it as a spec.

- **UX asymmetries surface in seconds.** Kyle smoked PR #89, the volume slider remembered its value across refresh, the profile dropdown didn't. Immediately weird. "Why does one persist and the other not?" My original design rationale ("drawer is live-only, doesn't overwrite per-mode defaults") was defensible in isolation but lost against the simpler user expectation that two controls in the same panel should behave the same way. **Rule:** when you ship two visually-paired controls, give them parallel persistence semantics by default; only diverge if there's a concrete reason.

- **The orchestrator workflow is institutional traceability, not mandatory liturgy.** PR #88 (4 new filter generators + 8 `<option>` entries + sw.js bump + new test file) had real risk surface — engine code, test harness precedent, multi-layer touches. The 5-phase audit→engine→tests→UI→ship pipeline earned its overhead. PR #89 (3 files, ~85 lines, no engine, no tests, pure additive UI) didn't. Trying to wedge it through the orchestrator was rationalization; going direct was correct. **Rule:** the orchestrator is for changes where a future you (or a teammate) will want to read the audit and understand why a tier was set. For mechanical UI follow-ups that consume an already-tested API, the PR description IS the audit trail.

- **Web Audio's gesture requirement is the load-bearing API rule.** Any audio code that wants to start in a non-gesture-handler context — page load, timer-fire, async callback after a fetch — has to either (a) chain off a previous user gesture that already unlocked the context, or (b) wait for the next gesture and claim it. Today's auto-resume hook is the explicit form of (b). **Rule:** if you're writing browser audio code, plan the user-gesture chain before you write any sound-generation code. Knowing where the unlock happens is more load-bearing than the synthesis math.

### Answer key

1. **Simplest:** white noise — `data[i] = Math.random() * 2 - 1` per sample, no filter, no state. **Most subjective:** gray. White through violet have well-defined spectral slopes (flat, −3, −6, +6, +6×2 dB/oct). Gray is defined by *perception*, not slope — its target is "subjectively flat to the human ear," which means inverse-A-weighting, which has no single correct implementation. The shipped version (pink + 2 kHz notch) is one defensible approximation; a real A-weighting biquad chain would be more accurate but is a 4-filter cascade with coefficients that are no longer human-readable. The amplitude scalar is also more by-ear than by-formula. Validating gray means *listening* and asking "does this sound qualitatively flatter than white?", not measuring an FFT.

2. **Bubble phase reasoning:** click events fire in three phases — capture (top-down), target (at the clicked element), bubble (bottom-up). Default `addEventListener` is bubble phase, meaning my handler runs AFTER the clicked element's own handler. Flow.start and Pomodoro.start are click handlers on the Start button; both call `SFX.startAmbient(flow_ambient_profile)` synchronously inside the click handler. By the time my bubble-phase listener runs, `SFX.getAmbientProfile()` already returns the flow/pomodoro profile, my null-check fails, my hook is a no-op. **If I listened on the capture phase:** my handler runs BEFORE the Start button's handler. I check `getAmbientProfile()` → null → I call `startAmbient(persistedProfile)`. Then microseconds later, the Start button's bubble-phase handler runs, calls `startAmbient(flowProfile)`, swaps the source. Audible glitch: ~50ms of brown noise (my persisted profile) before it swaps to pink (the Flow profile). Or worse, if the two profiles' buffers are both unloaded, two AudioContext spin-ups racing. Bubble phase is the right answer; capture would create a glitch race.

3. **Rule of thumb:** the orchestrator earns its overhead when (a) the PR touches multiple layers (engine + UI + tests + docs), (b) the change has a real risk surface (sync invariants, schema migrations, native bridges, security rules), (c) you want a future-reader to be able to reconstruct the why from the audit doc, OR (d) the diff has any sw.js cache bump, schema bump, or new persistence key (these auto-trigger medium tier and benefit from the structured Phase-5 push-gate). The orchestrator is overkill when the PR is purely additive UI consuming an already-tested API, has no risk surface, and the entire diff fits in a 60-second visual scan. Today's PR #88 hit (a), (b), (c), and (d) — full orchestrator. PR #89 hit only (d) (sw.js bump), which is a soft tier-bumper, not a workflow-mandator — direct ship was fine.

4. **Brief's contradiction:** the brief said two different things in two different places. (a) "Place them after the existing pink line" — given the current order Brown / Pink / White, this would put the new entries between Pink and White: Off / Brown / Pink / Green / Blue / Violet / Gray / White. (b) Smoke step 2 listed the expected order as "Off / White / Brown / Pink / Green / Blue / Violet / Gray" — which would require reordering the existing 3 entries to put White first. **Why append-only won:** keeping existing entries in their current order minimizes diff (3 lines of text-content change instead of an entire `<select>` rewrite × 2 blocks), preserves muscle memory for any user who's used the dropdown before, and matches the principle that the JS `AMBIENT_PROFILES` array order (which IS the contract for `getAmbientProfiles()`) doesn't have to match the UI render order (which is static HTML). Final visible order: Off / Brown / Pink / White / Green / Blue / Violet / Gray. Auditor recommended it, brief was overridden by the audit + user-review pause, didn't cost anything later.

5. **What `_ambientProfile !== null` guards against:** specifically, a click on the Pomodoro or Flow Start button being the *first* gesture after a cold boot. The Start button's click handler calls `SFX.startAmbient(per_mode_profile)` synchronously inside the click handler. My bubble-phase listener runs after that. Without the null-check guard: my hook reads `ambient_profile_last` from localStorage (e.g., "blue") and calls `SFX.startAmbient('blue')`. But ambient is already playing (the per-mode profile from Flow.start). `startAmbient` is idempotent for same-profile re-invocation but tears down + restarts when the profile changes. So `startAmbient('blue')` after Flow already started "pink" would tear down the pink source and start blue — actively wrong, the user starts a Pomodoro session and gets the WRONG color because of a stale localStorage value. The null-check turns the hook into a no-op when the engine already has a profile, preserving the session's intent.
